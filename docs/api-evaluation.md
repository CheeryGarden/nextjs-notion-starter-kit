# ofstar Connect Core - Open API 技术评估

> 场景：客户使用我们的硬件设备，但不使用我们的 SaaS 平台，需要通过 API 将设备数据传输到他们自己的平台。

## 0. 已确认的前置条件

| 项目 | 确认结果 |
|------|---------|
| **IoT 平台数据协议** | HTTP（已有 HTTP API） |
| **流媒体基础设施** | 已有流媒体服务器 |
| **数据实时性要求** | **秒级推送** |
| **同时对接平台数** | **10 个第三方平台** |

## 1. 需求概述

基于 ofstar Connect Core 产品文档，需要开放的数据能力覆盖以下模块：

| 模块 | 数据类型 | Plan 覆盖 |
|------|---------|-----------|
| **设备管理** | 设备注册、状态、基本信息 | 所有 Plan |

| **燃油数据** | 油量、剩余百分比、油耗率 | 所有 Plan |
| **OBD 数据** | 车速、发动机转速/水温/累计运行时间、电池电压、故障码 | 所有 Plan |

## 2. 容量规划（基于已确认条件）

### 2.1 数据吞吐量估算

以 **Plan 4 满配 2000 台设备 × 10 个第三方平台** 为最大规模基准：

| 指标 | 计算 | 结果 |
|------|------|------|
| 设备上报频率 | 秒级 ≈ 每设备每秒 1 条 | **2,000 条/秒** 写入 |
| Webhook 扇出 (fan-out) | 2,000 × 10 平台 | **20,000 条/秒** 推送峰值 |
| 每日数据量 | 2,000 × 86,400 | **1.73 亿条/天** |
| 每日 Webhook 投递 | 1.73 亿 × 10 | **17.3 亿次/天** |
| 告警事件（估算） | 平均每设备每天 5-20 条 | 1-4 万条/天 |
| 告警 Webhook | 4 万 × 10 | 40 万次/天（低频） |

### 2.2 关键约束

| 约束 | 影响 | 应对策略 |
|------|------|---------|
| **秒级延迟** | Webhook 投递必须 < 1s p99 | 内存队列 + 并发投递池，跳过落盘 |
| **10 路 fan-out** | 单条消息放大 10 倍 | 批量合并投递、per-tenant 连接池 |
| **HTTP 协议对接** | IoT 平台 HTTP API 有延迟 | 连接复用 (keep-alive)、并发请求 |
| **2000 设备** | 并不算大规模 | 单节点可承载，但推送需要分布式 |

### 2.3 推送方案选型

鉴于**秒级推送 × 10 个平台**，纯 Webhook（HTTP POST 回调）在极端场景下不是最优选，但对于当前规模（2000 设备）仍可行。推荐分两层实现：

| 推送方式 | 适用场景 | 延迟 |
|---------|---------|------|
| **Webhook (HTTP POST)** | 告警事件、设备上下线、RFID 等中低频事件 | < 1s |
| **Webhook 批量模式** | 远程信息秒级快照（可选 1-10s 批次合并） | 1-10s 可配 |
| **SSE / WebSocket（未来）** | 如客户需要更低延迟 | < 200ms |

**推荐 Webhook 为主**，对于秒级远程信息数据采用**微批量投递**（每 1-5 秒合并一批发出），平衡延迟与吞吐。

## 3. API 接口清单

### 3.1 认证 (Authentication)

| 接口 | 方法 | 路径 | 说明 |
|------|------|------|------|
| 获取 Token | POST | `/api/v1/auth/token` | 通过 appId + appSecret 获取 access_token |

### 3.2 设备管理 (Devices)

| 接口 | 方法 | 路径 | 说明 |
|------|------|------|------|
| 设备列表 | GET | `/api/v1/devices` | 分页查询设备列表，支持状态/关键字过滤 |
| 设备详情 | GET | `/api/v1/devices/:deviceId` | 获取单个设备详细信息 |

### 3.3 远程信息数据 (Telematics)

| 接口 | 方法 | 路径 | 说明 |
|------|------|------|------|
| 实时快照 | GET | `/api/v1/telematics/snapshot` | 获取设备最新一帧完整数据 |
| 历史数据 | GET | `/api/v1/telematics/history` | 分页查询历史远程信息数据（最长7天） |
| 轨迹查询 | GET | `/api/v1/telematics/trajectory` | 查询GPS轨迹（最长24小时） |

### 3.4 告警事件 (Alarms)

| 接口 | 方法 | 路径 | 说明 |
|------|------|------|------|
| 告警列表 | GET | `/api/v1/alarms` | 分页查询告警事件，支持类型/严重性过滤 |
| 告警详情 | GET | `/api/v1/alarms/:alarmId` | 获取单个告警详情（含关联媒体） |
| 确认告警 | PUT | `/api/v1/alarms/:alarmId` | 确认/取消确认告警 |
| 驾驶行为事件 | GET | `/api/v1/alarms/harsh-events` | 查询急加速/急减速/急转弯事件 |

### 3.5 视频服务 (Video) — Plan 3 & 4

| 接口 | 方法 | 路径 | 说明 |
|------|------|------|------|
| 实时视频 | POST | `/api/v1/video/live-stream` | 请求实时视频流（返回流地址） |
| 录像回放 | GET | `/api/v1/video/playback` | 按时间段查询录像回放 |
| 视频下载 | POST | `/api/v1/video/download` | 请求视频下载链接（最长1小时片段） |
| 告警视频片段 | GET | `/api/v1/video/clips` | 查询告警触发的录像片段 |

### 3.6 Webhook 数据推送

| 接口 | 方法 | 路径 | 说明 |
|------|------|------|------|
| 列表 Webhook | GET | `/api/v1/webhooks` | 查询所有 Webhook 配置 |
| 创建 Webhook | POST | `/api/v1/webhooks` | 注册新 Webhook（仅 HTTPS） |
| Webhook 详情 | GET | `/api/v1/webhooks/:webhookId` | 获取 Webhook 配置详情 |
| 更新 Webhook | PATCH | `/api/v1/webhooks/:webhookId` | 修改 Webhook 配置 |
| 删除 Webhook | DELETE | `/api/v1/webhooks/:webhookId` | 删除 Webhook |
| 投递日志 | GET | `/api/v1/webhooks/deliveries` | 查询 Webhook 投递记录 |

### 3.7 数据导出 (Export)

| 接口 | 方法 | 路径 | 说明 |
|------|------|------|------|
| 创建导出任务 | POST | `/api/v1/export` | 异步批量导出（JSON/CSV） |
| 查询导出状态 | GET | `/api/v1/export?taskId=xxx` | 查询导出进度和下载链接 |

**接口总计：19 个 API Endpoint**

### 4.2 关键技术决策

| 决策点 | 选定方案 | 理由 |
|--------|---------|------|
| **IoT 数据对接** | HTTP Client + 连接池 | 已确认 HTTP 协议，直接对接 |
| **认证方式** | HMAC-SHA256 签名 | M2M 场景，无需浏览器交互 |
| **数据推送** | Webhook + Redis Streams | 秒级要求 + 10 路 fan-out |
| **视频流** | HTTP 代理 → 现有流媒体服务器 | 已有流媒体，API 层做鉴权代理 |
| **异步任务** | Redis Queue + Worker | 导出、重试等后台任务 |
| **多租户隔离** | per-appId 限流 + 数据过滤 | 10 个平台需要独立限流和数据权限 |

### 4.3 多租户设计（10 个平台）

```
每个第三方平台分配：
┌──────────────────────────────────────┐
│ appId: "platform-a"                  │
│ appSecret: (HMAC 密钥)               │
│ ┌──────────────────────────────────┐ │
│ │ 设备权限: [device-001..device-200]│ │
│ │ Plan 级别: Plan 3                 │ │
│ │ 限流配额: 100 req/s               │ │
│ │ Webhook 配额: 5 个                │ │
│ │ 推送频率: 可配置 (1s / 5s / 10s)  │ │
│ └──────────────────────────────────┘ │
└──────────────────────────────────────┘
```

每个 appId 拥有：
- **独立的设备访问权限列表**（不能越权访问其他平台的设备）
- **独立的限流配额**（防止某平台异常拖垮全局）
- **独立的 Webhook 配置**（各自推送到自己的接收端）
- **按 Plan 级别开放能力**（Plan 1/2 无视频、Plan 3/4 全功能）

## 6. 风险与应对

| 风险 | 概率 | 影响 | 应对措施 |
|------|------|------|---------|
| IoT HTTP API 文档缺失或接口不稳定 | 中 | 高 | 提前获取文档，先做 Mock 对接 |
| 秒级推送 × 10 平台吞吐瓶颈 | 中 | 高 | Redis Streams 解耦，per-tenant 连接池隔离 |
| 某第三方平台接收端故障导致背压 | 高 | 中 | per-tenant 熔断，不影响其他 9 个平台 |
| 流媒体服务器 API 对接复杂度 | 低 | 中 | 已有服务器降低了方案选型风险 |
| 多租户数据泄露 | 低 | **极高** | 严格的 appId → 设备绑定 + 每次查询校验 |
| 大量历史数据查询性能差 | 中 | 中 | 加索引 + 分页限制 + 最大查询范围限制 |

### 技术难点排序

1. **Webhook 推送引擎 (fan-out × 10, 28 人日)**：20K/s 投递、per-tenant 隔离/熔断、秒级延迟保证 — 整个项目技术含量最高、工作量最大的部分
2. **IoT 平台 HTTP 适配层 (5 人日)**：数据格式映射、连接池管理、错误处理 — HTTP 协议降低了难度，但取决于 IoT API 文档质量
3. **多租户数据隔离 (3 人日)**：10 个平台各自设备权限、限流配额 — 安全性关键
4. **视频代理层 (12 人日)**：已有流媒体服务器，主要做鉴权和元数据 — 复杂度比预期低

### 整体评估

IoT 数据对接是 HTTP 协议（最通用的协议，对接成本最低），流媒体已有（视频模块复杂度大幅降低），这两个前置条件极大地简化了技术方案。

**最大的工作量集中在 Webhook 推送引擎（28 人日，占比 37%）**——秒级推送 × 10 路 fan-out × 2000 设备 = 20K/s 的投递吞吐，需要认真设计队列、连接池、熔断和重试机制。这是一个需要独立开发和压测的子系统。

其余部分（API 端点本身、认证、多租户）都是标准 CRUD + 鉴权，复杂度可控。
