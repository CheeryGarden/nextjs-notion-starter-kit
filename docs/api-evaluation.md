# ofstar Connect Core - Open API 技术评估

> 场景：客户使用我们的硬件设备，但不使用我们的 SaaS 平台，需要通过 API 将设备数据传输到他们自己的平台。

## 1. 需求概述

基于 ofstar Connect Core 产品文档，需要开放的数据能力覆盖以下模块：

| 模块 | 数据类型 | Plan 覆盖 |
|------|---------|-----------|
| **设备管理** | 设备注册、状态、基本信息 | 所有 Plan |
| **GPS 定位** | 实时位置、轨迹回放、里程 | 所有 Plan |
| **车辆远程信息** | 速度、怠速、累计里程、OBD 数据 | 所有 Plan |
| **驾驶行为** | 急加速、急减速、急转弯 | 所有 Plan |
| **传感器数据** | 旋转状态/方向/转速、胎压/胎温、温湿度 | 所有 Plan |
| **燃油数据** | 油量、剩余百分比、油耗率 | 所有 Plan |
| **OBD 数据** | 车速、发动机转速/水温/累计运行时间、电池电压、故障码 | 所有 Plan |
| **RFID 识别** | 刷卡司机识别 | 所有 Plan |
| **异常告警** | 通用异常告警 | 所有 Plan |
| **ADAS/DMS 告警** | 车道偏离、碰撞预警、疲劳驾驶、抽烟、打电话等 | Plan 3, 4 |
| **视频服务** | 实时视频、录像回放、视频下载 | Plan 3, 4 |
| **AI 功能** | ADAS/DMS/BSD 开关控制 | Plan 3, 4 |

## 2. API 接口清单

### 2.1 认证 (Authentication)

| 接口 | 方法 | 路径 | 说明 |
|------|------|------|------|
| 获取 Token | POST | `/api/v1/auth/token` | 通过 appId + appSecret 获取 access_token |

| 接口 | 方法 | 路径 | 说明 |
|------|------|------|------|

| 设备详情 | GET | `/api/v1/devices/:deviceId` | 获取单个设备详细信息 |

### 2.3 远程信息数据 (Telematics)

| 接口 | 方法 | 路径 | 说明 |
|------|------|------|------|

| 历史数据 | GET | `/api/v1/telematics/history` | 分页查询历史远程信息数据（最长7天） |
| 轨迹查询 | GET | `/api/v1/telematics/trajectory` | 查询GPS轨迹（最长24小时） |

### 2.4 告警事件 (Alarms)

| 接口 | 方法 | 路径 | 说明 |
|------|------|------|------|
| 告警列表 | GET | `/api/v1/alarms` | 分页查询告警事件，支持类型/严重性过滤 |
| 告警详情 | GET | `/api/v1/alarms/:alarmId` | 获取单个告警详情（含关联媒体） |
| 确认告警 | PUT | `/api/v1/alarms/:alarmId` | 确认/取消确认告警 |
| 驾驶行为事件 | GET | `/api/v1/alarms/harsh-events` | 查询急加速/急减速/急转弯事件 |

### 2.5 视频服务 (Video) — Plan 3 & 4

| 接口 | 方法 | 路径 | 说明 |

### 2.6 Webhook 数据推送

|------|------|------|------|

## 3. 数据推送方案 (Webhook)

除了客户主动拉取（Pull），还需要支持服务端主动推送（Push）机制：

### 3.1 支持的事件类型

| 事件 | 描述 | 触发频率 |
|------|------|---------|
| `device.online` | 设备上线 | 低频 |
| `device.offline` | 设备离线 | 低频 |
| `telematics.snapshot` | 定时远程信息推送 | 高频（可配间隔，默认30s） |
| `alarm.triggered` | 告警事件触发 | 中频 |
| `harsh_event.detected` | 激烈驾驶事件 | 中频 |
| `rfid.swipe` | RFID 刷卡 | 低频 |
| `video.alarm_clip` | 告警视频片段就绪 | 中频 |
| `geofence.enter` | 进入围栏 | 低频 |
| `geofence.exit` | 离开围栏 | 低频 |

### 3.2 Webhook 安全机制

- **HMAC-SHA256 签名**：每次推送在 `X-Webhook-Signature` 头中携带 HMAC 签名，客户验证数据完整性
- **仅 HTTPS**：Webhook URL 必须为 HTTPS
- **重试策略**：失败后指数退避重试（默认最多 3 次，间隔 5s → 10s → 20s）
- **投递日志**：保留完整投递记录供查询和排障

### 4.2 关键技术决策点

| 决策点 | 推荐方案 | 备选方案 |
|--------|---------|---------|
| **认证方式** | HMAC-SHA256 签名（适合 M2M 场景） | OAuth2 Client Credentials |
| **数据推送** | Webhook + 消息队列 | MQTT Broker / Server-Sent Events |
| **时序数据存储** | TimescaleDB / InfluxDB | AWS Timestream |
| **视频流** | HLS + CDN 加速 | WebRTC（低延迟场景） |
| **异步任务** | Redis Queue + Worker | AWS SQS + Lambda |
| **API 网关** | 自建中间件 | AWS API Gateway / Kong |

### 4.3 开发工作量拆分

| 模块 | API 数量 | 复杂度 | 说明 |
|------|---------|--------|------|
| **基础框架** | - | 中 | 认证中间件、错误处理、日志、限流、API 版本管理 |
| **认证模块** | 1 | 低 | Token 颁发/刷新，凭证管理 |
| **设备管理** | 2 | 低 | 对接现有设备数据源的 CRUD 查询 |
| **远程信息数据** | 3 | **高** | 需对接 IoT 平台数据通道，处理高频时序数据查询和聚合 |
| **告警事件** | 4 | 中 | 需对接多种告警源（ADAS/DMS/BSD/通用），含媒体关联 |
| **视频服务** | 4 | **高** | 需对接流媒体服务，处理实时流 / 回放 / 下载，涉及存储和转码 |
| **Webhook 推送** | 6 | **高** | 需实现完整推送引擎（队列、重试、签名、投递日志） |
| **数据导出** | 2 | 中 | 异步任务处理，大数据量 CSV/JSON 导出 |
| **文档与测试** | - | 中 | OpenAPI/Swagger 文档、集成测试、压力测试 |

### 4.4 复杂度与风险分析

#### 高复杂度模块

1. **远程信息数据 (Telematics)**
   - 需要对接现有 IoT 平台的设备数据通道
   - 时序数据查询性能优化（索引设计、分区策略）
   - 2000 台设备 × 30 秒上报间隔 = 约 **5,760,000 条/天**
   - 需要考虑数据聚合和降采样策略

2. **视频服务 (Video)**
   - 实时视频流：需要对接现有流媒体服务器或搭建新的 WebRTC/HLS 网关
   - 云端录像存储和检索：依赖 AWS S3 + 视频索引
   - 视频下载：需要生成有时效性的预签名 URL
   - 带宽成本可能较高

3. **Webhook 推送引擎**
   - 需要构建可靠的消息队列和投递机制
   - 高频事件（telematics.snapshot）每分钟可能产生 **4,000+** 条推送
   - 指数退避重试、死信队列、投递日志
   - 客户端故障时的背压处理

#### 主要风险

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| IoT 平台数据接口不明确 | 阻塞数据对接 | 提前摸清现有平台 API/协议 |
| 视频流方案选型 | 影响延迟和成本 | 评估现有流媒体基础设施 |
| 高频推送性能 | Webhook 投递延迟 | 消息队列解耦 + 批量投递 |
| 多租户隔离 | 数据安全 | 严格的 appId 鉴权 + 数据分区 |
| API 版本演进 | 客户兼容性 | v1 路径前缀 + 版本策略 |

## 5. 前置依赖 & 需要确认的问题

在正式进入开发前，需要确认以下关键问题：

### 5.1 数据源

1. **IoT 平台现有接口**：设备数据是通过什么协议/接口获取的？（MQTT、HTTP API、数据库直连？）
2. **数据存储**：现有远程信息数据存储在哪里？（时序数据库、关系数据库、对象存储？）
3. **告警数据来源**：ADAS/DMS/BSD 告警是设备端直接上报还是服务端分析生成？

### 5.2 视频基础设施

4. **流媒体服务**：是否有现成的流媒体服务器？用什么协议？（RTMP、GB28181、私有协议？）
5. **云端录像**：录像存储在哪里？如何检索？是否已有视频索引？
6. **CDN**：是否需要通过 CDN 加速视频分发？

### 5.3 客户需求

7. **数据推送频率**：客户对实时性的要求？（秒级 / 分钟级 / 按事件？）
8. **并发规模**：预计同时对接多少个第三方平台？
9. **数据格式偏好**：客户是否有特定数据格式要求？

### 5.4 合规与安全

10. **数据隔离**：多租户场景下的数据隔离方案
11. **审计日志**：是否需要完整的 API 访问审计？
12. **数据留存**：API 返回的数据留存策略（文档提到 6 个月数据存储）

## 6. 总结

### 工作量总览

| 阶段 | 接口数 | 关键交付 |
|------|--------|---------|
| Phase 1 | 10 | 认证 + 设备 + 远程信息 + 告警 + 文档 |
| Phase 2 | 8 | Webhook 推送引擎 + 数据导出 |
| Phase 3 | 4 | 视频流 + 回放 + 下载 |
| Phase 4 | TBD | 电子围栏 + AI 控制 + 高级功能 |

### 技术难点排序

1. **IoT 平台数据对接层** — 需要深入了解现有平台的数据模型和接口协议
2. **Webhook 推送引擎** — 全新组件，需保证高可用和数据一致性
3. **视频流媒体对接** — 依赖底层流媒体基础设施
4. **时序数据查询优化** — 大数据量下的性能保证

### 建议

- **优先启动 Phase 1**，这是客户最基本的需求，也能最快验证技术可行性
- **尽早确认前置依赖**（特别是 IoT 平台接口和视频基础设施），这是最大的不确定性
- **API 设计已完成框架代码**，可以先与客户对齐接口契约，再推进后端实现
- 建议采用 **OpenAPI/Swagger** 规范编写正式 API 文档，便于客户集成
